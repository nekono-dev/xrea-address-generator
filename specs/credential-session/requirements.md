# 認証情報セッション 要件定義書

## 1. 目的

利用者ごとのXREA認証情報とProton Passのアクセストークンを、サーバに平文で保存せずに保持し、要求ごとに取り出せるようにする。既定では暗号化したcookieだけで保持してサーバを無状態に保ち、セルフホストでは暗号化したSQLiteへの保存も選べるようにする。

## 2. スコープ

### 2.1 対象

- 認証情報の登録、疎通の確認、保持、取り出し。
- トークンを含む登録の要求での、連携の利用可否に応じたトークンの扱い。
- cookie方式とSQLite方式の2つの保持方式。
- 登録状態の問い合わせと、ログアウトと、未登録の要求の拒否。

### 2.2 対象外

- 登録画面。
- 利用者ごとのアカウントとパスワードによる認証（外部のアクセス制御に委ねる）。
- 発行済みのcookieの個別の失効（ログアウトはブラウザのcookieを消すだけで、複製されたcookieは期限まで有効）。
- 複数インスタンスから共有できる保持方式（D1・Postgres等のSQLクライアント）の実装。

## 3. 前提

- なし

## 4. 機能要件

- FR-1: XREAのアカウント・サーバ名・APIシークレットキーと任意のProton Passアクセストークンの登録を受け、XREAへの疎通を確認できたものだけを保持し、失敗は400にする。
- FR-2: 既定のcookie方式では、認証情報をAES-256-GCMで暗号化してcookieの値にし、サーバに認証情報を保存しない。
- FR-3: 起動オプションでSQLite方式を選んだとき、cookieにはセッションIDだけを入れ、暗号化した認証情報を、セッションIDに束縛して、差し替え可能なSQLクライアント経由で保存する。
- FR-4: cookieをHttpOnly・SameSite=Strict・有効期間7日で発行し、Secure属性は既定で付け、設定で外せるようにする。
- FR-5: 登録から7日を過ぎた認証情報と、改ざんされたcookieと、別の鍵で作られたcookieは、未登録として扱う。
- FR-6: 登録の有無・トークンの有無・期限を返す問い合わせと、cookieを消すログアウトを受け付け、秘匿値は返さない。
- FR-7: 登録済みの利用者が再登録したとき、新しい認証情報で置き換える。
- FR-8: 認証情報・暗号化鍵・暗号文を、応答とログに含めない。
- FR-9: 現行と直前の秘密値から鍵を導出して、暗号化に現行の鍵、復号に識別子の合う鍵を使い、32文字未満なら起動を拒否する。
- FR-10: 未登録の利用者の保護対象の要求に、認証情報の登録を求める401を返す。
- FR-11: cookie方式を、Node.jsとCloudflare Workersの両方で同一の実装により動かす。
- FR-12: Proton Passアクセストークンを含む登録の要求では、疎通の確認のあとに連携の利用可否を最新の状態で確認し、利用可能でなければトークンを保持せず、XREAの認証情報だけを保持して、トークンを保持しなかったことを示す200を返す。
- FR-13: 登録済みの利用者の登録状態の問い合わせ（ダッシュボードを開いたときに行う）で、同じ認証情報のcookieを有効期間7日で発行し直し、期限を延長する。

## 5. 非機能要件

- NFR-1: 認証情報の暗号化と復号を、それぞれ5ミリ秒以内に完了する。
- NFR-2: cookieの値を、4096バイト以下にする。
- NFR-3: SQLite方式で、期限切れの行を登録のたびに削除し、登録後の期限切れの行を0件にする。

## 6. 受け入れ条件

- AC-1 (FR-1): 正しい認証情報の登録要求でXREAへの疎通が確認され、cookieが発行される。
- AC-2 (FR-1): 疎通の確認が失敗する認証情報の登録要求が400になり、cookieが発行されない。
- AC-3 (FR-2): cookie方式で発行したcookieの値から、平文のシークレットキーが読み取れず、同じ鍵で復号すると元の認証情報に戻る。
- AC-4 (FR-3): SQLite方式で発行したcookieの値に認証情報が含まれず、データベースの行が暗号文だけを持つ。
- AC-5 (FR-4): 発行されたcookieにHttpOnly・SameSite=Strict・7日の有効期間があり、Secureは設定を外したときだけ付かない。
- AC-6 (FR-5): 7日と1秒後の要求・1文字改ざんしたcookie・別の鍵のcookieが、いずれも未登録として扱われる。
- AC-7 (FR-6): 登録後の問い合わせが登録済みと期限を返し、応答にシークレットキーとトークンが含まれない。
- AC-8 (FR-7): 2回目の登録後は、2回目の認証情報だけが取り出され、SQLite方式では最初の行が削除される。
- AC-9 (FR-8): 登録と取り出しを行った後の応答とログに、シークレットキーとトークンの文字列が含まれない。
- AC-10 (FR-9): 秘密値が未設定、または31文字のとき設定の読み込みが失敗し、32文字では成功する。
- AC-11 (FR-10): cookieを持たない保護対象の要求が401になり、後続の処理が呼び出されない。
- AC-12 (FR-11): Node.jsのテストとWorkersの実行環境のテストの両方で、cookie方式の保存と取り出しが成功する。
- AC-13 (NFR-1): 認証情報の暗号化と復号の所要時間が、それぞれ5ミリ秒以内である。
- AC-14 (NFR-2): 入力の上限長いっぱいの認証情報を暗号化したcookieの値が、4096バイト以下である。
- AC-15 (FR-3): 別のSQLクライアントの実装でも登録と取り出しが成功し、標準のsqlite3コマンドでデータベースを開いてセッションの表を参照できる。
- AC-16 (NFR-3): 期限切れの行を持つデータベースへの登録後、期限切れの行が0件になる。
- AC-17 (FR-12): 連携が利用可能なとき、トークンを含む登録の要求が204になり、トークンが保持されて、問い合わせの応答でトークンありになる。
- AC-18 (FR-12): 連携が未設定または利用不可のとき、トークンを含む登録の要求が200 { proton } を返し、cookieが発行され、XREAの認証情報だけが取り出され、問い合わせの応答でトークンなしになる。
- AC-19 (FR-12): トークンを含まない登録の要求では、連携の利用可否の確認が呼び出されず、204が返る。
- AC-20 (FR-12): 疎通の確認が失敗する登録の要求では、連携の利用可否の確認が呼び出されない。
- AC-21 (FR-9): 秘密値を入れ替えて、直前の秘密値に入れ替え前の値を指定すると、入れ替え前に発行したcookieから認証情報が取り出され、その後の登録は新しい鍵で暗号化される。
- AC-22 (FR-9): 秘密値を入れ替えて直前の秘密値を指定しないとき、入れ替え前に発行したcookieは未登録になる。
- AC-23 (FR-9): 直前の秘密値が31文字のとき設定の読み込みが失敗し、現行と同じ値のときは1つの鍵として扱われる。
- AC-24 (FR-3): 行の暗号文を別のセッションIDの行へ複製すると、複製先のIDで未登録になり、元のIDでは取り出せる。
- AC-25 (FR-6): ログアウトの要求が、有効期間0のcookieを返す204になり、登録済みの要求でも未登録の要求でも成功する。
- AC-26 (FR-13): 登録済みの問い合わせの応答に7日の有効期間のcookieが付き、期限が延長され、そのcookieで同じ認証情報を取り出せる。未登録の問い合わせではcookieを発行しない。
- AC-26 (FR-6): SQLite方式でログアウトすると行が削除され、ログアウト前のcookieの値を再送しても未登録になる。
