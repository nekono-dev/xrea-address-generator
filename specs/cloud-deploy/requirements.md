# クラウド配備 要件定義書

## 1. 目的

XREAゲートウェイをDurable Objectとして内蔵したアプリをCloudflare Workersの無料枠に配備し、Proton Pass読み取りサービスを任意のコンテナ基盤で動かせるようにする。コンテナに求める条件と、秘匿値の与え方と、配備後の疎通確認を、基盤に依存しない形で定める。そのうえで、具体例としてCloudflare WorkersとGoogle Cloud Runでの構築手順と、構成を示す図を提供する。Proton Pass読み取りサービスを配備しない構成も選べるようにする。

## 2. スコープ

### 2.1 対象

- Workersへの配備の定義と、画面ファイルの配備。
- コンテナ基盤に求める条件と、読み取りサービスのイメージの利用。
- 秘匿値と接続先の設定、配備後の疎通確認。
- Cloudflare WorkersとGoogle Cloud Runを例にした、構成の図と構築手順。
- 配備後の運用（保持方式、秘密値の更新、失効、インスタンス数）の手順。
- 構成例のすべてのコンポーネントを、再実行しても同じ結果になる形で一括配備するスクリプトと、一括撤去するスクリプト。

### 2.2 対象外

- 例に挙げた以外のコンテナ基盤の手順と、基盤の契約・課金の設定。
- Cloudflare Accessとアカウントの設定。
- セルフホストのDocker構成。
- SQLite方式の認証情報の保持。

## 3. 前提

- なし

## 4. 機能要件

- FR-1: ゲートウェイを内蔵したアプリを、Workersの無料枠で動く単一のスクリプトと画面ファイルとして配備できる定義を提供する。
- FR-2: 暗号化の秘密値と、読み取りサービスを使うときの共有シークレットをWorkersの秘密として、読み取りサービスのURLを変数として設定する。
- FR-3: 読み取りサービスを動かすコンテナ基盤に、最大インスタンス数1、HTTPSでの公開、共有シークレットの設定を求める。
- FR-4: 読み取りサービスのURLを設定しないとき、読み取りサービスのコンテナを配備せずにProton Pass連携なしで動かせる。
- FR-5: 読み取りサービスを配備するとき、コンテナを共有シークレットを知らない呼び出し元から拒否し、セッションの保存先を再作成を許す一時領域にする。
- FR-6: 配備後に、Workersの死活と、内蔵ゲートウェイを通したXREAへの到達と、読み取りサービスへの疎通を確認する手順と検査を提供する。
- FR-7: 配備を、手動の実行だけで行え、秘匿値をリポジトリとログに残さない。
- FR-8: Workersの画面ファイルに、版を含むファイルの1年間のキャッシュと、入口の毎回の検証を指示する。
- FR-9: 利用者・Workers（ゲートウェイを内蔵）・読み取りサービス・外部サービスの関係と、配備の順序を、構成の図で示す。
- FR-10: Google Cloud Runに、読み取りサービスを、秘匿値をSecret Managerに置いたまま構築する手順を示す。
- FR-11: 運用の手順書に、保持方式がcookieに固定される理由と、秘密値の更新、全利用者の失効、インスタンス数の固定を示す。
- FR-12: 構成例を1つのコマンドで冪等に一括配備でき、同じタグで入れ直せ、別のコマンドで情報を残さず一括撤去できる。

## 5. 非機能要件

- NFR-1: Workersのスクリプトの圧縮後のサイズを、無料枠の上限の3メガバイトより小さい1メガバイト以下にする。
- NFR-2: Workersの1要求あたりのCPU時間を、無料枠の上限10ミリ秒以内にする。
- NFR-3: 配備後の疎通確認を、60秒以内に完了する。

## 6. 受け入れ条件

- AC-1 (FR-1): 配備の定義の検証が成功し、スクリプトと画面ファイルの出力先と、ゲートウェイ用のDurable Objectの束縛が定義に含まれる。
- AC-2 (FR-2): 秘密と変数の一覧が、必要な設定をすべて含み、秘匿値の実値が定義に含まれない。
- AC-3 (FR-3): コンテナ基盤の要件の検査が、最大インスタンス数が2以上、またはHTTPで公開されている構成を失敗にする。
- AC-4 (FR-4): 読み取りサービスのURLを空にした構成で、アプリが読み取りサービスを呼び出さずに一覧を返す。
- AC-5 (FR-5): 共有シークレットなしの読み取りサービスへの要求が401になり、一時領域のセッションを失っても再ログインで取得が再開する。
- AC-6 (FR-6): 疎通確認の検査が、Workersの死活確認と、偽の認証情報がXREAに拒否されたこと、読み取りサービスの死活確認と共有シークレットの一致を報告する。
- AC-7 (FR-7): 配備の手順が手動の実行だけで完了し、リポジトリとログに秘匿値の文字列が含まれない。
- AC-8 (FR-8): 配備した画面ファイルの応答ヘッダが、版を含むファイルに1年のキャッシュを、入口に毎回の検証を指示する。
- AC-9 (NFR-1): ビルドした成果物の圧縮後のサイズが、1メガバイト以下である。
- AC-10 (NFR-2): 一覧の要求の処理で、入出力の待ちを除いたCPU時間が10ミリ秒以内である。
- AC-11 (NFR-3): 配備後の疎通確認が、60秒以内に完了する。
- AC-12 (FR-9): 手順書に構成の図が含まれ、図に4つの構成要素と配備の順序が現れる。
- AC-13 (FR-10): Cloud Runの手順が最大インスタンス数1と秘匿値のSecret Manager経由の設定を含み、実値と予約された環境変数 PORT の指定を含まない。
- AC-14 (FR-11): 運用の手順書が、cookie方式の固定、直前の秘密値を使う更新の手順、全利用者の失効の手順、最大インスタンス数1の理由を含む。
- AC-15 (FR-12): 一括配備がコンテナ、Workersの順に進み、既存のサービスとイメージがあるときだけ、サービス、イメージの順に同じタグのまま削除してから入れ直す。
- AC-16 (FR-12): 一括配備が作成済みの共有シークレットと設定済みのCOOKIE_SECRETを変更せず、秘匿値をコマンドの引数に載せず標準入力だけで渡す。
- AC-17 (FR-12): 手順書が事前準備、クイックスタート、配備手順の順に節を持ち、クイックスタートに個別のデプロイの手順を含まない。
- AC-18 (FR-12): 一括撤去がWorkers、サービス、リポジトリ、シークレットの順に存在するものだけを削除し、何も残っていなくても成功する。
